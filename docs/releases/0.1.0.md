# NLMX 0.1.0: relatório de release

Data: 2026-10-03 · Máquina de verificação: Apple M4, 16 GB, macOS 27.0.1 · Artefato: `dist/NLMX.dmg`

**Resumo:** o app instala a partir do DMG e roda sozinho, sem `runtime/`, sem Homebrew, sem Ollama e sem Python. Ele baixa e confere o modelo, e funciona offline em todo o fluxo: importação, RAG, chat, citações e viewer, usando o runtime de dentro do bundle. **Não está pronto para distribuição pública**: falta assinatura Developer ID e notarização, porque não há certificado nesta máquina. O pipeline (`make release`) está pronto e aguarda o certificado.

## Requisitos mínimos

- **macOS 27** ou superior.
- **Mac com Apple Silicon** (sem Intel, sem Rosetta).
- **Apple Intelligence ativado** e licença do `fm` aceita (`sudo fm license`).
- **Disco:** ~50 MB para o app, mais 640 MB para o modelo e espaço para a biblioteca e os índices.
- **Memória:** observado em uso o app com ~33 MB, o `llama-server` com ~1,9 GB e o `fm serve` com ~16 MB (o modelo do sistema roda nos processos do macOS). **Recomendado: 16 GB.**
- **Rede:** só para baixar o modelo (uma vez). Depois disso, o app funciona 100 % offline.

## Limitações

- **Sem notarização neste build:** em outros Macs, o Gatekeeper exige clique direito › Abrir. Isso não é aceitável para distribuição pública.
- **Sem OCR:** PDFs escaneados são marcados como "sem texto" e não entram na busca.
- **Sem atualizador automático** (decisão de produto): atualizar = instalar o DMG novo. Os dados são mantidos.
- **Janela de contexto do Apple FM (4 096 tokens):** limita cada resposta a ~1 800 tokens de trechos. Perguntas que exigem muitos trechos são respondidas com parte deles.
- **Perguntas sobre "seção N"** dependem de títulos numerados reconhecidos. Quando não há título correspondente, a pergunta vai para a busca normal.
- **Documentos muito repetitivos:** páginas quase idênticas que só mudam números podem gerar respostas "não encontrei". Na aceitação, 1 de 9 perguntas, todas sobre um PDF sintético de 200 páginas padronizadas.
- **Embeddings lentos** (8,4/s) e `llama-server` com ~1,9 GB de memória, pelo contexto de 8 192 tokens e lote de 2 048.
- **Um processo do app por vez** sobre a mesma pasta de dados. Fechar o app com `kill` (em vez de Sair) pode deixar um `fm serve` órfão, limpo na próxima geração.

## Problemas encontrados (e status)

Encontrados por esta verificação de release:

| Problema | Impacto | Status |
|---|---|---|
| O cliente HTTP dos downloads estava **sem TLS** (`reqwest` sem features). Todo download `https://` de modelo falharia no app real; os testes usavam servidores HTTP locais | Crítico: nenhum modelo poderia ser baixado | **Corrigido** (`native-tls`) + teste que exige HTTPS no cliente e URLs `https` no catálogo |
| "cláusula 1 do contrato" era tratada como pedido da "seção 1": só a seção 1 de outro documento ia para o modelo | Respostas erradas ou "não encontrei" | **Corrigido**: a seção é complementada pela busca normal |
| Seção pedida sem título correspondente respondia "não encontrei a seção" sem buscar no texto | Perdia respostas existentes | **Corrigido**: cai na busca normal |
| Remoção de quase-duplicatas podia descartar trechos padronizados com números diferentes (limite 0,8, caso real 0,786) | Risco de perder tabelas e cláusulas numeradas | **Corrigido**: exige os mesmos números |
| Ad-hoc + hardened runtime: a validação de bibliotecas recusava todas as dylibs do bundle | Crítico: o app não carregaria PDFium nem llama.cpp | **Corrigido** (etapa de empacotamento): hardened runtime só com Developer ID |

Encontrados nas etapas anteriores (todos corrigidos e cobertos por testes):
- caixas e texto errados em páginas rotacionadas;
- citações e fontes que não abriam o viewer, e página escura ao reabrir (comportamentos do HTMX 4);
- campo do chat sem posição fixa;
- vazamento de caminhos e nomes de arquivo nos logs.
